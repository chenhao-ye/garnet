# Full Replication Sweep (v2): Performance Report

Reader-heavy replication sweep on `code-replication` (branch `chenhaoy/replication-bench`, backpressure + drain fix), run under pinned maximum CPU frequency. Two matched 180-combo grids: **v2** (AofMemorySize 1 GB per sublog) and **v2_summem** (AofMemorySize as a fixed 1 GB total, split 1 GB/m per sublog).

## 1. Setup

**Topology.** primary=node0 (10.10.1.1), replica=node1 (10.10.1.2), client=node2 (10.10.1.3); all 144 hardware threads (2x36 cores, SMT). Diskless sync, main-memory (null-device) AOF.

**CPU frequency.** run.py pins the `performance` governor on all three nodes in the prepare step (turbo on, ~3 GHz). This removes the DVFS artifact that made reader throughput spuriously scale with writer count; these numbers are the trustworthy ones. See `code_CLAUDE.md` ("CPU frequency must be pinned").

**Fixed knobs.**

| Knob | Value |
|---|---|
| dbsize | 10,000,000 keys |
| key / value length | 8 B / 8 B |
| reader threads | 16 (itp=256) |
| writer/reader pipelining | itp=256 |
| runtime x repeats | 30 s x 3 (median reported) |
| AOF memory (v2) | 1 GB per sublog |
| AOF memory (v2_summem) | 1 GB total => 1g/m per sublog (1g,256m,128m,64m,32m) |
| ship budget / replica budget | 256 MB / 256 MB (summed over sublogs) |
| replay tasks per sublog (n) | 1 |

**Swept (6 x 5 x 6 = 180 combos each grid).**

| Dimension | Values |
|---|---|
| writer threads | 1, 2, 4, 8, 16, 32 |
| physical sublogs m | 1, 4, 8, 16, 32 |
| replay-drift barrier | 10k, 30k, 100k, 300k, 1M, 2.4M ticks (4us..1ms) |

**Workload.** Concurrent on the client: writer threads SET on the primary over the 10 M keyspace; 16 reader threads GET on the replica; 1 freshness prober writes a versioned key on the primary and polls the replica for it (end-to-end visibility). Throughput in Mops/s, latency in microseconds, lag in bytes.

## 8. AofMemorySize: per-sublog vs fixed-total (v2 vs v2_summem)

Fixed-total memory split per sublog performs the same as 1 GB per sublog, even at m=32 where per-sublog memory drops 32x (1g -> 32m). Writer-throughput ratio per m, averaged over all writers and drifts:

| m | per-sublog mem (summem) | writer ratio summem/persublog | mean lag 1g (MB) | mean lag summem (MB) |
|---|---|---|---|---|
| 1 | 1g | 1.029 | 381.3 | 375.4 |
| 4 | 256m | 0.985 | 68.1 | 69.7 |
| 8 | 128m | 0.994 | 27.8 | 27.5 |
| 16 | 64m | 0.988 | 9.8 | 11.1 |
| 32 | 32m | 0.994 | 5.4 | 4.9 |

All ratios within +/-3% (noise). Reason: null-device AOF + FastAofTruncate makes each sublog a continuously-truncated circular buffer whose occupancy is bounded by the 256 MB lag budgets (8 MB/sublog at m=32), not by buffer size; as long as per-sublog memory exceeds the per-sublog lag share, buffer size never binds. Implication: a fixed 1 GB total costs 32x less memory at m=32 with no perf loss. Boundary: only holds while per-sublog memory > per-sublog lag budget.
